# Design and compatibility

## Product boundary

Timestamp Only is a single, unprivileged, sandboxed AppKit process. It owns the menu-bar status item, Settings window, selected-folder bookmark, FSEvent stream, candidate queue, and same-directory rename operations. Launch Services is configured to prohibit multiple instances of the app. It has no XPC service, privileged helper, package installer, telemetry, screenshot decoder, or network client.

A small embedded login item exists only for the macOS 11 and 12 launch-at-login fallback. It launches the main app and then remains idle; it never receives the folder bookmark or screenshot-folder access. macOS 13 and later register the main app directly with `SMAppService.mainApp`. Service Management can report `.notFound` before it has seen a fresh installation, so that state is presented as off and an opt-in attempts registration. Only an unknown future status disables the control.

## Compatibility

The source deployment target is macOS 11. The build compiles separate `arm64-apple-macosx11.0` and `x86_64-apple-macosx11.0` products and combines them with `lipo`, so operating-system support and processor support remain separate dimensions:

- Apple silicon Macs run the native arm64 slice
- Intel Macs run the native x86_64 slice
- Both slices declare macOS 11 as their minimum operating system

The core APIs predate macOS 11, but the supported floor is constrained by the active Xcode toolchain and the cost of testing older systems. A deployment target proves link compatibility, not runtime behavior. Big Sur and Monterey require dedicated runtime qualification of security-scoped bookmarks, screenshot metadata, FSEvents, the login helper, relaunch, sleep and wake, replacement upgrades, and removal before a release can claim support.

Newer Service Management behavior is availability-gated at macOS 13. The interface uses AppKit `NSStatusItem` and an ordinary programmatic Settings window rather than newer SwiftUI menu-bar and Settings scene APIs.

## Permission model

The app enables App Sandbox, user-selected read/write file access, and app-scoped bookmarks. `NSOpenPanel` records the user's explicit folder selection. On later launches the app resolves the stored bookmark, refreshes it if stale, calls `startAccessingSecurityScopedResource()`, and provides Choose Folder Again recovery if access fails. Apple documents each step in [Accessing files from the macOS App Sandbox](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox).

This design avoids Full Disk Access and does not try to read another process's private `com.apple.screencapture` preferences. Desktop is the initial folder-picker location; the surrounding copy directs users to the Screenshot toolbar's Options menu when they use a custom destination.

## Detection and event handling

Original filename text is never evidence because Apple localizes screenshot names and users can customize the base name. A candidate must carry a positive `com.apple.metadata:kMDItemIsScreenCapture` value. A positive screen-recording marker excludes it. These keys are observable macOS behavior but not a documented public API contract, so the reader is isolated behind a protocol and missing or invalid values fail closed.

The watcher requests file-level events, watches root changes, reduces its own events, and treats every notification as an advisory wakeup rather than a complete transaction. Apple says file events can be coalesced or dropped, requires rescanning on `MustScanSubDirs` and dropped-event states, and recommends starting monitoring before the initial snapshot; see [Using the File System Events API](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html). Apple's [`IgnoreSelf`](https://developer.apple.com/documentation/coreservices/1455376-fseventstreamcreateflags/kfseventstreamcreateflagignoreself) flag reduces feedback notifications generated by the app itself.

The app starts its stream before establishing a baseline. Existing file identities are remembered but never enqueued. Create and rename events enqueue new candidates, duplicate notifications merge by device and inode, and dropped events compare a fresh directory snapshot with the baseline. Only direct-child regular files are eligible.

Candidates must have stable size, creation time, and modification time across consecutive probes. A startup-race event or dropped-event rescan result is admitted only when all available filesystem dates are from the active monitoring session, which avoids treating a user move or rename of an old screenshot as a new capture. Delayed capture metadata is retried with bounded policy, and a later event can reconsider an expired candidate. A bounded recent-identity cache and own-event filtering stop the app's rename from feeding back into another rename.

The candidate's device and inode are checked before classification and again immediately before the exclusive rename. If the path was replaced in between, the candidate is abandoned without changing the replacement.

Pausing tears down the watcher and pending queue. Resuming starts a fresh stream and baseline, deliberately leaving files created during the pause untouched.

## Timestamp choice

The filename timestamp uses this order:

1. Filesystem creation time
2. Metadata content-creation time
3. First-observed time
4. Rename time

Filesystem creation time best represents when a normal screenshot file appeared and survives localization. Content creation metadata is useful on volumes without a creation date but can lag Spotlight indexing. First-observed time is independent of filename conventions but shifts if processing is delayed. Rename time is always available but least faithful to capture time. The original filename is never parsed because both its words and timestamp format can vary.

Dates earlier than 2001 or implausibly far in the future are rejected before moving to the next source. The formatter uses a Gregorian calendar and `en_US_POSIX` locale, with either the auto-updating local time zone or UTC.

## Safe rename

The destination preserves the source extension. Collision candidates progress through the unsuffixed name, `-1`, `-2`, and later numeric suffixes.

Each attempt calls `renamex_np` with `RENAME_EXCL`, which atomically refuses an existing destination. A check followed by an overwriting move is never used. Apple exposes whether a volume supports this primitive through [`volumeSupportsExclusiveRenaming`](https://developer.apple.com/documentation/foundation/urlresourcevalues/volumesupportsexclusiverenaming). Unsupported filesystems fail visibly instead of weakening the no-overwrite guarantee.

## Formats and recordings

A positive capture marker admits still-image types recognized by macOS and PDF while preserving the original extension. PNG is not hardcoded. Screen recordings are excluded because they have their own marker, use video containers, and can remain partially written much longer. Recording support would require a separate opt-in product decision, completion model, and test matrix.

## Distribution and updates

The primary artifact is a Developer ID signed, hardened, notarized, and stapled DMG with the app and an Applications shortcut. A `.pkg` offers no concrete benefit because the app is self-contained and installs no external agent or privileged component. It would add an Installer certificate, package receipts, elevated installer UX, and more complex removal.

A Homebrew Cask is the secondary path and consumes the identical DMG. Stable semantic versions, predictable artifact names, bundle identity, and SHA-256 output prepare for both Cask upgrades and a future update feed.

Version 1 has no updater code or network entitlement. A future updater can sit outside the renaming core, reuse release metadata, and require explicit opt-in; automatic checks default to off.
